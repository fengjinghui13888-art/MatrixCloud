## 5. 本轮修复的问题

- 多账号同时保存抢占浏览器前台：同电脑保存草稿改为有界串行队列；同账号重复请求拒绝，读取同步仍独立。
- 平台草稿库异步读取卡住：分阶段超时、只读重试、晚到连接关闭；不可读绝不视为空草稿箱。
- 平台将空段落序列化为制表符、普通标签存于正文：只兼容这两种确证格式，正文/标签/图片不一致仍阻止完成回执。
- 迁移后新增租户的目录被旧用户清单误判，以及旧设备绑定复活：后续升级以 PG 为主，旧 SQLite 不再导回已迁租户。
- 账号删除后迟到同步重新创建账号：导入只允许已存在账号；扫码确认的新账号有单独创建路径。
- 丢失模型解密密钥：不覆盖或误建新密钥，要求恢复原密钥。
- 任务超时：主任务与执行记录一起结束，防止状态一直运行。
- 窄屏个人中心隐藏：团队管理入口保持可达。

## 6. 维护、升级与迁移

日常先检查 `/api/health` 的 `storage=postgresql/schema=2`、连接器在线状态、磁盘剩余空间及失败任务。当前容器默认开机恢复，TLS 每 6 小时检查续期；电脑关闭/休眠、平台登录过期仍需处理。

升级流程：构建新的不可变镜像 → 暂停新请求、确认无在途任务 → 文件数据备份 + PG dump → 执行版本化 schema/兼容迁移 → 启动替换容器 → 健康与连接器检查 → 开放访问。不能把旧 SQLite 版本直接启动来回滚现在的 PG 写入。

手动 PG 备份（在服务器，以具有 Docker 权限的维护身份执行；文件含客户数据，勿公开）：

```sh
sudo python3 /home/ubuntu/matrix-cloud-releases/20260915-tenant-db-v6/scripts/postgres_backup.py /home/ubuntu/matrix-cloud-backups/manual-YYYYMMDD.dump
```

该命令生成 custom-format dump、SHA256 清单并检查归档可读取。另需保留媒体目录、模型加密密钥、TLS 和连接器配置；数据库 dump 单独不能恢复媒体或解密配置。

恢复先在新空数据库执行 pg_restore，使用迁移身份建立 schema 与应用权限，核对数量/哈希后才切换应用连接文件。恢复密钥必须与备份的密文对应。生产写入开放后如需回退，优先回退兼容 PG schema 的应用镜像；不可把旧备份直接覆盖当前生产库。

换服务器迁移：备份 PG + 文件/媒体 + 独立保管密钥 → 新机部署同版本 PG/应用 → 恢复至新库/目录 → 校验 → 配置 HTTPS/域名 → 切换客户连接器云端地址并重新配对 → 实测账号同步和草稿。Chrome 登录态不保证跨电脑复制有效；新执行电脑应逐账号扫码。

当前未启用定时异地加密备份，部署前本机备份不等于灾备。自动每日 7–30 天保留、COS/异地目标、加密密钥托管、告警属于下一阶段。没有云存储凭证时不虚构已经配置。
